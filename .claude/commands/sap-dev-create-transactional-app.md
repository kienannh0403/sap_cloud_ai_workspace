## Phase 2 — Runtime Verify Loop: self-verify UI + read side, manual lifecycle scenarios (max 3 iterations)

Start only once all Phase-1 objects are activated and have passed [Skill: activation-guard] (no open Gate-3 ripple issues, no `REGRESSED` rows). The expected side of every check is the **spec** — TS + `artifacts/targets/[AppName]/fs/fs_markdown.md` (FS incl. transcribed mockups) — never a fixed checklist and never "what the build happens to contain". Save every raw output under `artifacts/targets/[AppName]/build/odata_verify/`. The self-run steps never write: Create/Update/Delete/actions stay manual (2.M) — no POST/PATCH/DELETE from scripts.

2.0a PRECONDITION — can the read-only client see this build? Business data is readable only on the read-only server (client 100; the write client 080 returns 0 rows — no data-read authorization). Run `bash .claude/scripts/odata-verify/fetch.sh samecode <TYPE> <NAME>` for the root Projection View, its Metadata Extension (once the user has created it) and the Behavior Pool. All `SAME` → 2.0b/2.U. Any `DIFFERENT`/`http…` → skip 2.0b/2.U, everything goes manual (2.M) and the ledger records why.

2.0b READ-SIDE DATA VERIFY (self-run). Service URL: `fetch.sh srvurl <read-only server> <SRVB>`. For the root and every composition child entity set: every field of TS §3 via `fetch.sh sample … '$top=20&$select=<all fields>'` (a field `EMPTY in every row` is a FAIL unless the spec allows it), and every read-side rule of TS §5 (derived/virtual fields, status values that must exist, hardcoded filters) as OData `$filter` count assertions per the case matrix below, whose expected `total` is written down BEFORE running. The script never prints field values (`.claude/exceptions/`). Anything not expressible as a count assertion → 2.M.
  **Case matrix (minimum per spec item; each case = one `TC-nn` row in the 2.3 log, its Case column naming the kind: dương / âm / biên / filter):**
  - **Every rule of TS §5** (derived field, complex logic, hardcoded filter, status that must/must not appear) → **2 cases**: *dương* — rows that satisfy the rule, expected `total=N` (exact N when the spec/test data fixes it, otherwise `total>0` for a value known to exist); *âm* — rows that violate the rule, expected `total=0` (e.g. rule "only released PRs" → `$filter=<status> ne '<released>'` → `total=0`).
  - **Rule with a threshold or range** (date/period, quantity, amount, "from–to", "≥ / <") → **+ biên cases**: one at exactly the boundary value and one just outside it, expected result per the spec's inclusive/exclusive wording (if the spec does not say which, that is a TS gap → ask the user, do not guess).
  - **Every parameter/filter of TS §2** → **2 cases**: a value known to exist → `0 < total ≤` unfiltered total; a value known not to exist → `total=0`. CDS input parameters: also one call without the parameter → expected error. Mandatory-filter enforcement and default values are UI behaviour (annotations) — they are checked in 2.U, not here.
  - Write every expected outcome in the checklist BEFORE running any query. A case that cannot be expressed as a count assertion, or for which the tenant has no suitable data, keeps the same dương/âm/biên design but moves to 2.M for the user — never marked PASS here.

2.U UI VERIFY (self-run, spec-driven): build `artifacts/targets/[AppName]/build/ui_checklist.md` — one row per UI requirement found in TS §2/§4/§7 AND in `fs_markdown.md`, for the List Report AND the Object Page of every node (columns and order, exact label wording, selection fields, mandatory filters, value help, default values, sort/group, text-for-code display, toolbar actions and their enablement, facets per node, field groups, hidden/read-only/mandatory fields, currency/unit formatting, anything else the FS says): `| ID (UI-nn from TS, or new) | Requirement | Source (TS §x / FS section) | Proof: metadata / manual | Result | Evidence |`. FS ↔ TS disagreement is a TS defect → STOP and ask the user (`sap-dev-rule.md` §6). Then `fetch.sh metadata …` + `node .claude/scripts/odata-verify/ui-check.js <metadata.xml> --ddlx <DDLX source file(s)>`; judge each row PASS/FAIL quoting the output line. Rows metadata cannot prove (rendering, F4 returning rows, action enablement at runtime, manifest.json settings like frozen columns, formatting) → `Proof: runtime`: run [Skill: fiori-ui-check] on the deployed app (or its preview mode over the published service binding when none is deployed yet), read-only client, **VI and EN logon** — value help per filter, search, `rows`, `columns`, `actions` (enabled/disabled, never pressed), `open_row` + `facets` for every node's object page — and judge each such row from the step results **and the screenshots** (PASS/FAIL with that evidence); any new defect it shows is an extra `UI-nn` FAIL.
